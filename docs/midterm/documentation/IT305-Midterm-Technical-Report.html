2. Introduction and Problem Statement

The Small Inventory and Supplier System addresses fragmented inventory, request, borrowing, reservation, incident, supplier, and purchasing records used by three school offices: the Property Custodian Office, Hospitality Management Laboratory Office, and Science Laboratory Office. Paper forms and disconnected spreadsheets make it difficult to maintain consistent stock balances, enforce office responsibility, trace approvals, and preserve a reliable history.

SISS provides a local web application where requesters can submit and track requests, office personnel can perform office-scoped operations, office heads can approve and adjust authorized records, and administrators can manage the system across offices. This midterm report focuses on four verified integration milestones: architecture, a consumed API response, secure category CRUD, and authenticated role-restricted access.

3. System Objectives and Scope

Objectives

  • Centralize inventory and supplier-related records for the three offices.
  • Provide authenticated, role-aware access for requesters, office personnel, office heads, and administrators.
  • Use database constraints, controlled functions, grants, and row-level security (RLS) to protect records.
  • Maintain traceable stock, request, circulation, incident, procurement, notification, and audit history.
  • Demonstrate working integration between the browser, Next.js, Supabase Auth, PostgREST/RPC, and PostgreSQL.

Checkpoint scope

Implemented: local authentication, six application roles, three office scopes, catalog and soft deactivation, stock and operational workflows, dashboard health integration, RLS, and automated tests.

Browser verified: login, admin dashboard, health status, category create/read/update/deactivate, student login, and student rejection from an administrator route.

Planned or incomplete: hosted deployment, production email/password recovery, private incident attachment delivery, scheduled notifications, configurable multi-step approvals, production monitoring, and representative-user evaluation.

4. Week 1 — Integration Plan v2

The implemented design follows a medium application architecture: a Next.js entry point delegates to a feature service or Server Action, which owns Supabase access. Presentation components do not own database security. PostgreSQL remains the final data authorization and integrity boundary.

  1. The browser renders React pages and submits forms or requests JSON.
  2. Next.js Route Handlers, Server Components, and Server Actions validate the request and resolve the authenticated user.
  3. Supabase Auth establishes identity and supplies the user UUID used by application authorization.
  4. Feature services use typed Supabase table queries or controlled RPC functions.
  5. PostgreSQL grants, RLS, constraints, and transactions enforce access and consistency beside the data.

The detailed source plan is stored at docs/midterm/week-1-architecture/integration-plan-v2.md.

5. Week 1 — Architecture Diagram and Data Flow

Authentication flow

  1. The browser submits email and password to signInAction.
  2. Supabase Auth validates the account and issues a cookie-backed session.
  3. src/proxy.ts refreshes the session during navigation.
  4. requireActiveUser loads the profile and roles and rejects inactive accounts.
  5. Role/office guards protect the route or action, and PostgreSQL RLS protects the operation.

API flow

The dashboard renders ApiHealthStatus, which requests GET /api/health, validates HTTP success and {"status":"ok"}, and renders either “System API Online” or a safe unavailable state.

Category data flow

Authorized forms call validated Server Actions. Supabase query builders issue parameterized operations. RLS checks active role and office scope. Category removal is implemented as is_active = false so historical references remain intact.

10. Week 4 Authentication and Role-Based Access

SISS uses Supabase email/password authentication. Public registration is disabled locally. Protected layouts call requireActiveUser; administrator pages call requireAdmin; inventory uses office-aware server guards. PostgreSQL RLS repeats authorization beside the data operation.

The schema supports student, teacher, non_teaching, office_staff, office_head, and admin. Office staff and office heads are limited to assigned offices; administrators operate across offices. The evidence run verified an admin session and an isolated student session. A direct student request to /admin/users returned HTTP 404.

A read-only aggregate query against the local Supabase Auth schema returned five authentication users, five users with a stored password hash, and five hashes matching the bcrypt format. No identity or hash value was selected. These counts demonstrate the local stored-hash format but do not alone prove password strength, secure transport, access governance, or every aspect of password security.

11. Setup and Run Instructions

  1. Install Node.js 22.14 or newer, npm 11.19 or newer, and Docker Desktop.
  2. Run npm install initially. Use npm ci after the lockfile is committed.
  3. Copy .env.example to the ignored .env.local and set the local public Supabase URL and publishable key. Do not commit the file.
  4. Start the local stack with npm run supabase:start.
  5. Start the web application with npm run dev -- --hostname 127.0.0.1 --port 3000.
  6. Open http://127.0.0.1:3000.

Checkpoint safety: do not run supabase db reset while preserving local demonstration accounts and evidence data.
